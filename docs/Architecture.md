# Архитектура проекта

## Структура

Проект делится на **core**, **common** и **feature** модули:

1. **Core** – базовые сущности и инфраструктура, доступная всем модулям: сеть, база данных,
   глобальные интерфейсы, конфигурации.
2. **Common** – общие утилиты, расширения, константы, компоненты UI и функции, которые повторно
   используются в разных feature.
3. **Feature** – конкретные функциональные модули приложения (например, авторизация, профиль, лента
   новостей).

Внутри каждого подмодуля есть подструктуры:

1. **Data** – слой данных, реализация репозиториев, источники данных (локальные, удалённые).
2. **Domain** – бизнес-логика: UseCase, интерфейсы репозиториев, сущности.
3. **DI** – компоненты для внедрения зависимостей, модули Dagger Hilt.
4. **Presentation** – уровень представления: View (Activity/Fragment/Composable), ViewModel.
5. **Utils** – вспомогательные классы и расширения, которые не относятся напрямую к бизнес-логике,
   но упрощают работу с Domain и Presentation (например, расширения для коллекций, форматы дат,
   конвертеры данных).

**Дальнейшее видение:**

- **Четкое разделение абстракций и реализаций:** возможно стоит рассмотреть использование api/impl
  подхода.

---

## MVVM

Архитектура строится по принципу **MVVM**:

View <-> ViewModel <-> Model

- **View** – отображает данные и реагирует на действия пользователя.
- **ViewModel** – обрабатывает события, подготавливает данные для View, обращается к UseCase.
- **Model / Domain** – бизнес-логика, репозитории, источники данных.

MVVM обеспечивает четкое разделение ответственности, упрощает тестирование и интеграцию с DI.

**Дальнейшее видение:**

- **Частичное использование MVI:** крупные экраны, например главная, могут постепенно перегрузиться
  логикой. Более четкое разделение потока данных позволит нам легче контролировать логику и
  поддерживать сервис.

## DI

**Описание:**  
Dagger Hilt используется для управления зависимостями в проекте, чтобы исключить ручное создание
объектов и упростить тестирование компонентов.

**Взаимодействие компонентов в нашем проекте:**

- **ApplicationComponent** – глобальный компонент, живущий на протяжении всего приложения. Здесь
  создаются глобальные зависимости: синглтоны репозиториев, базы данных, сетевые клиенты.
- **Feature / Activity / Fragment Components** – наследуют зависимости из ApplicationComponent и
  предоставляют их локально для конкретного модуля или UI-компонента.
- **Modules (`@Module`)** – описывают правила создания зависимостей (`@Provides`, `@Binds`) и
  позволяют конфигурировать их для разных слоев.

**Обоснование использования:**

- Обеспечивает чистое разделение зависимостей между слоями Presentation, Domain и Data.
- Упрощает масштабирование приложения: при добавлении новых feature нет необходимости вручную
  передавать зависимости через конструкторы.
- Улучшает тестируемость: ViewModel и UseCase можно легко подменять mock-объектами.

**Дальнейшее видение:**

- **Переезд на manual DI:** со временем дерево зависимостей может разрастись, для оптимизации сборки
  возможно стоит перейти на runtime решения, например ручной DI.
